# SoroSLO v0.1.0

SoroSLO v0.1.0 is the first public release of the self-hosted synthetic service-level monitor for Stellar/Soroban applications.

## What ships

- strict, versioned `soroslo.yml` configuration;
- Testnet, Mainnet, and custom Stellar RPC configuration;
- simulation-only Soroban invocation engine;
- deterministic return normalization and assertions;
- ordered multi-step checks with prior-step result references;
- explicit `pass`, `service_fail`, `observer_error`, and `cancelled` semantics;
- SQLite evidence persistence and versioned migrations;
- restart-safe fixed-interval scheduler;
- rolling run-based SLI, SLO, observer coverage, and error-budget calculations;
- incident opening/recovery state machine;
- signed generic webhook delivery with retry and deduplication;
- Fastify API and Next.js operator dashboard;
- loopback-by-default security and bearer authentication for remote API exposure;
- Docker Compose deployment;
- unit, integration, and Playwright E2E tests;
- Rust/Soroban Testnet acceptance fixture and scheduled/manual live evidence workflow.

## Security boundary

The SoroSLO runtime does not accept Stellar secret seeds, mnemonic phrases, signing keys, or wallet sessions. It builds simulation transactions and calls Stellar RPC `simulateTransaction`; it does not sign or submit transactions.

The M6 Testnet acceptance workflow does create a temporary funded Testnet identity solely to deploy the public fixture contract. The SoroSLO acceptance process itself receives only the resulting public contract ID.

## Reliability semantics

v0.1 uses a run-based success-rate SLI. Observer errors are excluded from the service availability denominator and reported separately as monitor-health coverage.

SoroSLO does not claim exact wall-clock downtime from periodic samples.

## Intentional non-goals

v0.1 does not provide:

- transaction signing or submission;
- TTL remediation;
- deployment/upgrade management;
- full event indexing;
- multi-RPC failover;
- Prometheus/OpenTelemetry export;
- source verification;
- protocol compatibility packs;
- arbitrary plugins or JavaScript assertions;
- multi-user RBAC or hosted SaaS;
- Postgres;
- mobile applications;
- AI-generated incident explanations.

## Verification

Release readiness requires:

- green main CI;
- Docker Compose validation;
- Playwright E2E;
- successful real Stellar Testnet acceptance evidence;
- documented fixture contract/evidence;
- contributor-ready backlog.

See `docs/testnet-acceptance.md`, `docs/operations.md`, and `docs/threat-model.md`.
